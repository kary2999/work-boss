# 开发心得与使用说明

这篇文章回答两个问题：**这套“监工”是怎么一步步做出来的、踩过哪些坑**（第一部分），以及**拿到它之后怎么用**（第二部分）。概念见 [concept.md](concept.md)，每一步的详细记录见 [what-was-done.md](what-was-done.md)，数据格式见 [data-contract.md](data-contract.md)。

# 第一部分　开发心得

## 1. 起点：一个人的“计划—执行—回报—顺延”问题

使用者是一位产品经理，近期的工作是照着一款交易所 App 的合约模块，在 Axure 里画一套移动端原型：先定规范（375 宽画布、间距、外边距），再做母版库，再按页面逐个画。工作量大、琐碎、周期长，很容易出现三件事：

1. 早上的计划到晚上说不清做了没有；
2. “做了”没有证据，自己说、agent 说都不算；
3. 今天没做的事明天悄悄消失。

最初的需求只有一句话：**每天 08:30 告诉我今天做什么，20:30 问我做得怎么样。** 后面所有功能，都是这个闭环被现实一步步逼出来的。

## 2. 需求是怎么长出来的

需求不是一次想清楚的，而是在使用中被反馈推着变的。下面按时间整理，这也是最值得复盘的部分。

| 阶段 | 用户提出的 | 落成的东西 |
|---|---|---|
| 1 | 熟悉工作内容，建仓库，多 agent 协作要有约定 | 本地仓库＋`AGENTS.md`（目录、认领、计划、日志、隐私红线） |
| 2 | 08:30 发今日计划，20:30 问进度，要一个“监工” | 定时脚本 `supervisor.py` 的早间／晚间命令 |
| 3 | 用 Lark 沟通，和另一个 agent 共用机器人，**不能影响它** | 只用 REST，不开长连接；建专用“监工”群 |
| 4 | 没回复就每半小时问一次，到 0 点，记旷工 | 追问（21:00–23:30）和 00:00 收尾，旷工有明确定义 |
| 5 | 别只发文字，要用 Lark 的卡片、任务这些原生形式 | 互动卡片＋Lark 任务／子任务（勾选＝完成） |
| 6 | 回复了但没点完成；次日计划要能多选 | 完成只认勾选；回复或评论算“有回应”，不再催；未完成的任务顺延 |
| 7 | 本地要有工作日志看板 | `docs/dashboard.html`，五个分页 |
| 8 | 看板没变化；本地没同步进度；次日计划要本地维护；需求不足要在 Lark 提示 | 每个命令收尾统一刷新；进度回写任务卡；次日计划草案；“需求不足”主动要需求 |
| 9 | 按合约需求拆页面、拆功能；截图作为参考；任务里要带图 | 37 张切片任务卡，每张带验收项和参考图，建任务时作为附件上传 |
| 10 | 作废的删掉；文字全部简体中文 | 删除作废卡；全仓库简体化并用脚本复查 |
| 11 | 看板图片显示破图 | 查明是预览窗格不支持本地相对路径；加提示和本地白名单小服务 |
| 12 | 把看板、任务、日志维护到 Lark 知识库，图片一起传 | `wiki_sync.py`：页面结构与本地看板五个页签一致，任务卡和日志每条一页，图片上传 |
| 13 | 开源概念和做法，但**不能上传我的工作日志** | 公开仓库＋`.gitignore`＋`check_private.sh` 双层把关 |

回头看，有一个规律：**每一次“功能完成”之后，用户的下一条消息几乎都是“但是……”**。这不是需求没沟通好，而是“是否好用”只有跑起来才看得见。所以第 8 条之后我改变了做法：先把自己能验证的验证完（读真实数据、跑真实命令），再交付，而不是交付后等人发现问题。

## 3. 几条真正有用的设计取舍

**3.1 完成只有一种来源：你的勾选。** 监工看不到你的工作成果，所以它不判断质量，也永远不把“没证据”当“已完成”。这条看似保守，却是整个系统可信的地基。

**3.2 定时的动作交给脚本，不交给大模型。** 最初的定时任务是“每次让 AI 读提示词再干活”，结果输出不稳定，还出现过重复建任务。改成确定性脚本后，准点、可重复、可单元测试；AI 只负责拆任务、写计划、分析原因。

**3.3 顺延，不重建。** 没做完的任务是把**原来的** Lark 任务改期，而不是新建一个。评论、子任务进度、历史都留在原处，任务列表也不会被一堆逾期副本污染。

**3.4 文件就是总线。** 计划、任务卡、日志、状态全是文件。任何 agent 会读写文件就能参与，不绑定某个工具；这也是“多 agent 协作”能成立的原因。

**3.5 共用机器人，只用 REST。** 同一个 Lark 应用开第二条长连接，事件会被分流，等于抢另一个系统的消息。所以只用无状态的 REST，不订阅事件。代价是没有按钮回调，卡片只能展示和跳转；“多选”也就改成了用任务勾选来实现。

**3.6 私有数据不进公开仓库。** 工作日志、任务卡、计划、配置、截图都不入库；`check_private.sh` 在提交前扫描。这条是用户明确的底线，也是我每次提交前都跑检查的原因。

## 4. 踩过的坑（挑最有教训的）

完整清单在 [what-was-done.md](what-was-done.md)，这里只记**教训**。

| 坑 | 教训 |
|---|---|
| 估时算错（把约 33 小时说成 2.5～3 天） | 数字要加总再说，不凭印象；错了要明说并更正 |
| 把“测量页面、写规范”排给了用户 | 先弄清谁做什么：规范该由 agent 给，人只负责画 |
| 任务卡没写 `est_hours`，大任务被当成 1h，误报“需求不足” | 缺省值会制造假警报；关键字段要强制、要在文档里写明 |
| 子任务默认指派给用户，26 条刷屏 | 为了“能勾选”而牺牲了列表可读性；默认不指派 |
| 顺延覆盖了任务描述，里面有人补的规范被洗掉 | 改期只改时间和标题；**不可逆的覆盖要先想清楚**（那次丢的内容没能恢复） |
| launchd 读不到外接卷（`Operation not permitted`） | 装完定时任务不等于能跑；安装脚本要自测，失败就拦下并给出办法 |
| 看板图片破图，我一开始以为是路径错 | 先复现再下结论：真正原因是预览窗格把页面当静态快照 |
| 知识库写入：先 131006（没权限），后 1770001（参数无效） | 权限有两层：应用的 API 权限＋文档本身的编辑权限，**缺一层都报错**；两层错误码不同，要分开看 |
| 知识库上传图片报 1061044 | 知识库文档上传素材必须带 `drive_route_token` |
| 每次同步都全部重写 | 哈希里含了“最近更新”时间；内容无关的字段要排除在比较之外 |

## 5. 几点方法上的体会

1. **先让它能跑，再让它好看，但别跳过验证。** 能读到真实数据（Lark 任务、评论、附件）才算“通”。读回确认，比“接口返回成功”可靠。
2. **用户的截图是最好的需求文档。** 多次是看了用户的 Lark 截图才发现：卡片排版不对、没有点完成、图片是破的。
3. **能并行的就并行。** Lark 读取从串行 146 秒降到约 35 秒；知识库全量同步从 8～10 分钟降到约 115 秒。慢不是常数，往往只是没想到并行。
4. **增量比全量重要。** 内容哈希让日常同步不到一秒；没有它，每天四次全量重写既慢又容易触发限流。
5. **诚实交付。** 没验证的就写“没验证”，做错的就写“做错了”，丢了的东西就说“丢了”。这个系统本身就是“不给没证据的事记功”，开发它的人也该这样。

## 6. 现在的状态与没做完的事

已具备：确定性监工脚本、任务切片与参考图、自动刷新的本地看板、进度回写、次日计划维护、需求不足主动要需求、Lark 知识库同步、私有数据检查，共 52 个单元测试通过。

没做或没完全验证的：

- launchd 定时任务因仓库在外接卷上无法安装，目前由 Claude 应用里的定时任务暂代（只能启用其中一种）；
- 还缺 7 张高优先级参考截图（订单类型下拉、限价单表单、平仓流程、止盈止损展开、订单记录页、保证金弹窗、成功／失败提示），对应任务暂时只能按已有图做；
- Mini 合约、模拟交易等页面没有排进计划；
- 多人／多群、与 issue tracker 的对接都没做；
- 早间“顺延项改期”在真实 Lark 上的完整一天，还要靠接下来几天的真实运行来确认。

# 第二部分　使用说明

## 1. 它每天做什么

| 时间 | 监工做什么 | 你做什么 |
|---|---|---|
| 08:30 | 按计划建 Lark 任务（含子任务、起止时间、参考图附件），在群里发“今日工作项”卡片 | 按时段做；做完在任务里**勾选完成** |
| 20:30 | 发“今日进度询问”卡片：绿＝全完成、橙＝部分、红＝没有证据 | 把没勾的处理掉，或在任务**评论**写原因 |
| 21:00–23:30，每 30 分钟 | 对“未完成且没有说明”的任务发“第 N 次催促” | 勾选，或写评论（写了就不再催） |
| 00:00 | 收尾：判定是否旷工；未完成项**原任务改期**到次日；定稿次日计划 | 看一眼，有疑问写评论 |
| 白天（每小时或定点） | 同步进度、更新次日计划草案、刷新看板与知识库；发现需求不足就在群里问 | 随时看看板 |

**怎么回应监工**

| 你的动作 | 效果 |
|---|---|
| 勾选主任务 | 计为完成，停止催促 |
| 勾选子任务 | 计入子任务进度，不影响主任务判定 |
| 在任务评论里写原因 | 算“有说明”，不再催，不算旷工；任务仍会顺延 |
| 对监工的提问卡片点“回复” | 算已回报，当晚停止追问 |
| 什么都不做 | 催到 23:30，00:00 记旷工并顺延 |

旷工的定义很窄：全天没有任何勾选、没有任何评论、对提问也没有回复。它只代表“没回应”，不代表“没做事”。

## 2. 工作量不够时怎么补

某天的计划工时低于下限（默认 4 小时）时，监工会在群里发“需求不足”卡片。补法有三种：

| 做法 | 说明 |
|---|---|
| **对卡片点“回复”，每行写一条需求**（最快） | 例如 `画导航栏 2h`；没写估时按 1h。下次监工运行时并入当天计划 |
| 在 `tasks/` 复制 `_TEMPLATE.md` 新建任务卡 | **一定要写 `est_hours`**，否则按 1h 算，会拉低计划工时 |
| 让 agent 写 `plans/日期.json` | 把 `generated_by` 设为 `human` 或 agent 名，监工就不会覆盖 |

同一天最多主动要 3 次，两次至少隔 90 分钟，00:00 收尾再要 1 次。

## 3. 三个地方看进度

### 3.1 Lark 任务（干活用）

每个任务的**附件**就是对应的参考图，描述里列了验收项。在这里勾选完成。

### 3.2 本地看板 `docs/dashboard.html`

每个监工命令结束时自动重新生成。五个分页：

| 分页 | 内容 |
|---|---|
| 概览 | 今日主任务、明日计划工时与“需求不足”、旷工、你补充的需求、今日／明日计划、最近日志 |
| 进度 | 每天一张表：任务是否完成、子任务进度、你写的原因、催促次数 |
| 计划 | 每天的时段计划，低于下限标红 |
| 任务卡 | 按状态分组，含从 Lark 同步回来的进度 |
| 日志 | 全部工作日志 |

注意：

- 用**浏览器**打开（`open docs/dashboard.html`）。不要用编辑器的预览窗格，它会让本地相对路径的图片显示成破图。
- 一定要在预览窗格里看时，运行 `python3 scripts/serve_dashboard.py 8777`，再打开 `http://127.0.0.1:8777/docs/dashboard.html`。这个小服务只监听本机，只放行 `docs/` 与 `参考图组/`，其他一律 403。
- 页面顶部的“数据生成于”是最近一次监工运行的时间。

### 3.3 Lark 知识库

知识库根目录下有“**工作计划**”，结构和本地看板的五个页签一致：

```
工作计划
├─ 概览        指标、提醒、今日与明日计划、任务卡、最近日志、旷工
├─ 进度        每天的完成情况与你写的原因
├─ 计划        全部日期的时段计划
├─ 任务卡      按状态分组
│   └─ S01 … S37、T001   每张卡一页：属性、目标、验收项、参考图
└─ 工作日志    索引表
    └─ 每篇日志一页（最近 60 篇）
```

注意：

- 页面由脚本**整页重写**，在页面里手改的内容下次同步会丢。要补充说明，请写在任务评论或本地日志里。
- 页面包含**工作日志全文**，能看到页面的人就能看到这些内容；任务卡里的参考图是第三方截图。请确认该页面的可见范围。
- 内容没变的页面会跳过，日常同步通常不到几秒；首次或加 `--force` 才全量重写。

## 4. 任务卡与参考图

任务卡在 `tasks/`，从 `tasks/_TEMPLATE.md` 复制。关键字段：

```yaml
id: S11
title: 持仓卡片
status: todo          # todo | doing | review | done | blocked | cancelled
est_hours: 2.5        # 一定要写
phase: P-2
page: A17
images: 参考图组/20261017/合约-持仓.jpg   # 多张用 | 分隔；建任务时作为附件上传
```

- `status` 与 `progress` 由监工从 Lark 回写，**只往前走（待办→进行中→待验收），永远不会设为已完成**，也不降级。你不需要手动维护它们。
- 验收项（`- [ ]`）由 owner 勾选；“已完成”需要人确认。
- 作废的任务把 `status` 改成 `cancelled`，它会从计划和顺延里排除。

## 5. 多 agent 怎么参与

规则全文见 [AGENTS.md](../AGENTS.md)，要点：

1. 开工前读 `AGENTS.md`、`PROJECT.md`（若有）、今日计划、相关任务卡、最近 3 份日志。
2. **认领**：把任务卡的 `owner` 改成自己，`status` 改成 `doing`，并**立即提交**；未提交的认领无效。
3. 写计划：在 `plans/YYYY-MM-DD.json` 写，`generated_by` 设为 `human` 或自己的名字。`generated_by` 为 `supervisor` 的文件会被监工重新生成。
4. 写日志：`worklog/YYYYMMDD-HHMM-<agent>-<task-id>.md`，只新增、不修改；如实写做了什么、怎么验证、**没做／没验证什么**、风险和下一步。
5. 每个 agent 用独立的 worktree 和分支，禁止 `push --force`。
6. 不要手改 `.supervisor/`。

## 6. 第一次安装

详细步骤见 [setup-macos.md](setup-macos.md)，这里是顺序：

1. **准备 Lark**：在企业里用同一个机器人应用，把它拉进“监工”群；开通消息、任务、云文档等权限并发布版本。密钥放在仓库之外的 env 文件。
2. **配置**：复制 `config/lark.example.json` 为 `config/lark.json`，填群和负责人标识、env 文件路径。这个文件是私有的，不入库。
3. **先试跑**：
   ```bash
   python3 scripts/supervisor.py morning --dry-run    # 预览将建立的任务与卡片，不发消息
   python3 scripts/supervisor.py status               # 今日任务与提问状态
   ```
4. **选一种定时方式（同一时间只能启用一种，否则会重复发消息）**：
   - launchd：`bash scripts/install_launchd.sh`。仓库放在外接卷上会因系统隐私保护读不到，安装脚本会自测并拦下；放到家目录，或给 Python 完全磁盘访问权限即可。
   - Claude 应用里的定时任务：过渡方案，依赖应用在运行。
5. **可选：知识库同步**：在 `config/lark.json` 加 `wiki` 配置（`space_id`、父节点，留空则建在根目录）。机器人需要**两层权限**：应用后台开通并发布 `wiki:wiki`、`docx:document` 等，**并且**在知识库里把应用加为“可编辑”成员。缺第二层会报 131006。

## 7. 常用命令

```bash
# 监工
python3 scripts/supervisor.py status                 # 今日任务与提问状态
python3 scripts/supervisor.py morning --dry-run      # 预览早间要建的任务与卡片
python3 scripts/supervisor.py morning --date 2026-10-18   # 提前为某天建任务（会真实建任务并发卡片）
python3 scripts/supervisor.py sync                   # 立刻同步进度、次日计划、看板、知识库

# 看板
python3 scripts/build_dashboard.py                   # 只重新生成本地看板（不读 Lark）
python3 scripts/serve_dashboard.py 8777              # 本机白名单小服务

# 知识库
python3 scripts/wiki_sync.py --dry-run               # 列出每页的大小与图片数，不碰 Lark
python3 scripts/wiki_sync.py                         # 增量同步
python3 scripts/wiki_sync.py --force                 # 全部页面重写
python3 scripts/wiki_sync.py --out 看板.md           # 导出单页 Markdown（没有写权限时手动导入）

# 提交前
python3 -m unittest discover -s tests
bash scripts/check_private.sh
```

## 8. 常见问题

| 现象 | 原因与处理 |
|---|---|
| 看板没变化 | 看页面顶部“数据生成于”；它只在监工命令结束时刷新。可手动 `supervisor.py sync` |
| 看板里图片是破的 | 用浏览器打开，或用 `serve_dashboard.py`；不要用预览窗格 |
| 误报“需求不足” | 检查任务卡有没有写 `est_hours` |
| 知识库同步报 131006 | 机器人对页面没有编辑权限；在知识库里把应用加为可编辑成员 |
| 知识库同步报 1770001／1061044 | 脚本已处理（写块前清理字段；上传图片带 `drive_route_token`）。如仍出现，说明 Lark 接口有变化，需要查 |
| 收到重复消息 | 同时启用了两种定时方式；只保留一种 |
| 机器人收不到别的系统的消息 | 不该发生：监工只用 REST。如发生，检查是否有人为它开了长连接 |
| 想重置状态 | 见 [maintenance.md](maintenance.md)，不要手改 `.supervisor/` |

## 9. 隐私与边界

- **不入库**：`worklog/*`、`tasks/T*.md`、`plans/*.json`、`.supervisor/`、`config/lark.json`、`PROJECT.md`、参考截图、任何 `oc_`／`ou_`／`cli_` 开头的真实标识、任何密钥。
- 密钥只放在仓库之外的 env 文件；不要在日志或聊天里贴出来。
- 本系统不修改与它共用机器人的其他系统（如 Hermes）的任何配置。
- 对外发送（Lark 消息、GitHub 推送、知识库写入）属于对外动作，由维护者或有明确授权的流程执行。
- 文字一律使用**简体中文**，用语按中国大陆习惯。

## 10. 最后的建议

如果只记三件事：

1. **做完就勾选，做不完就写评论原因。** 这是监工认的唯一“证据”。
2. **任务卡一定写 `est_hours`。** 否则需求充不充足的判断会失真。
3. **想看进度，先看知识库或本地看板顶部的更新时间，再看内容。** 过期的看板比没有看板更误导人。
