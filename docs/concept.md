# 監工系統：概念與想法

## 1. 要解決什麼問題

一個人（可能帶著好幾個 AI agent）同時做多件事時，常見三種失控：

1. **計畫停在腦子裡**：早上想好今天做什麼，到晚上說不清做了什麼、沒做什麼、為什麼沒做。
2. **「做沒做」沒有證據**：自己說做了，或 agent 說做了，但沒有一個不依賴嘴的、可核對的記錄。
3. **沒做完的事悄悄消失**：今天沒做的事，明天沒人記得要接著做，或被新的事擠掉。

監工要做的就是一件事：**把「計畫 → 執行 → 回報 → 順延」閉成環，並且每一步都留下證據。**

## 2. 核心閉環

```
        ┌──────────── 08:30 發今日工作項 ────────────┐
        │                                            ▼
   00:00 收尾                                    人／agent 執行
   順延＋重排明日                                  （勾選完成 / 評論原因）
        ▲                                            │
        └── 21:00–23:30 每30分鐘催促 ◄── 20:30 詢問進度 ◄┘
```

| 時間 | 動作 | 做什麼 |
|---|---|---|
| 08:30 | morning | 讀 `plans/今日.json`，為每項工作建 Lark 任務（含子任務、起止時間），發「今日工作項」卡片 |
| 20:30 | evening | 讀任務勾選與評論，算完成度，發「今日進度詢問」卡片 |
| 21:00–23:30（每 30 分） | chase | 沒完成又沒說明原因的，發「請點擊完成」卡片催促；全部完成或已說明就停 |
| 00:00 | close | 判定是否旷工；未完成項**沿用原任務改期**順延；生成次日計畫檔 |

## 3. 設計原則

1. **證據優先，不替人宣稱完成。** 「完成」只有一種來源：你在 Lark 任務裡勾選。監工看不到你的工作成果，所以它**永遠不會**把「沒證據」當成「已完成」，也不會替你報完成。
2. **回應方式用平台原生動作，不發明格式。** 勾選任務、在任務評論寫原因、對提問消息點「回覆」——都是 Lark 自帶的操作。不要求你背格式、不要求你開新工具。
3. **順延，不重建。** 沒做完的任務不是新建一個副本，而是把原任務改期。評論、歷史、子任務進度都留在原處，任務列表也不會被重複項污染。
4. **有原因就是有回應。** 做不完可以，但要說為什麼。有評論說明＝有回應，不算旷工。
5. **旷工的定義很窄，並且標明可信度。** 旷工＝全天沒有任何主任務被勾選、沒有任何評論、對提問也沒有回覆。它只代表「沒回應」，不代表「沒做事」；若當天追問次數不足（例如電腦休眠），記錄裡會註明可信度較低。
6. **定時動作是確定性的，不依賴 LLM。** 排程只跑腳本（`scripts/supervisor.py`）。AI 的價值在「寫計畫、拆任務、分析原因」，不在「準點發消息」。這樣斷網、換模型、換 agent 都不影響監工準時。
7. **檔案就是總線。** 計畫、任務、日誌、狀態都是倉庫裡的檔案。任何 agent 只要會讀寫檔案就能參與，不需要綁定某個工具或對話。
8. **只用 REST，不碰別人的連線。** 與其他系統（例如已佔用機器人長連接的另一個 agent）共用同一個 Lark 機器人時，監工只調用無狀態的 REST，不開第二條長連接，避免搶消息。
9. **失敗要出聲。** 腳本失敗會寫 `*-supervisor-error.md` 並盡力在群裡發「監工執行失敗」，不能靜默。
10. **可關閉、可回滾。** 一條命令卸載定時任務；所有私有資料都在不入庫的目錄裡。

## 4. 角色

| 角色 | 職責 | 不做什麼 |
|---|---|---|
| **人** | 做事；在 Lark 勾選、寫評論；決定優先級 | — |
| **執行 agent** | 領任務卡、做事、寫日誌、勾驗收項 | 不改別人認領的任務；不改 `.supervisor/` |
| **排程 agent（可選）** | 寫 `plans/YYYY-MM-DD.json`：把任務卡拆成時段與子任務 | 不整個覆蓋別人的計畫 |
| **監工腳本** | 定時發任務、發卡片、收集結果、催促、順延、記旷工 | 不判斷工作品質；不替人完成 |

## 5. 名詞定義

| 詞 | 定義 |
|---|---|
| 工作項 | 計畫檔 `items[]` 的一條，對應一個 Lark 主任務 |
| 主任務／子任務 | 工作項／工作項下的細分清單（Lark 子任務，默認不指派，避免刷屏任務列表） |
| 完成 | Lark 任務被勾選完成（`completed_at` 非 0） |
| 有說明 | 未完成但使用者在任務評論寫了原因 |
| 回應 | 完成、有說明、或對提問消息有回覆，三者任一 |
| 旷工 | 當日沒有任何回應（見原則 5） |
| 順延 | 未完成主任務改期到次日，並排在次日計畫最前 |

## 6. 已知限制

- 排程要求電腦當時開著；休眠期間的觸發會在喚醒後補跑，但可能晚於預期，追問次數也可能不足。
- 監工只能依 Lark 與倉庫證據判斷，看不到你的設計稿／程式碼本身。
- Lark 沒有給應用發起原生「投票」的接口；卡片按鈕若要回傳結果必須走回調（長連接或 webhook），本系統刻意不用，因此卡片只有展示與開連結。
- 評論讀取依賴機器人應用的任務／消息讀取權限，見 docs/setup-macos.md。

## 7. 非目標

- 不是專案管理工具，不管甘特圖、資源、預算。
- 不評價工作品質，不給績效分數。
- 不替代 issue tracker：它只負責「今天的事有沒有被做、沒做的怎麼辦」。
