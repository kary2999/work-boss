# 监工系统：概念与想法

## 1. 要解决什么问题

一个人（可能带着好几个 AI agent）同时做多件事时，常见三种失控：

1. **计划停在脑子里**：早上想好今天做什么，到晚上说不清做了什么、没做什么、为什么没做。
2. **“做没做”没有证据**：自己说做了，或 agent 说做了，但没有一个不依赖嘴的、可核对的记录。
3. **没做完的事悄悄消失**：今天没做的事，明天没人记得要接着做，或被新的事挤掉。

监工要做的就是一件事：**把“计划 → 执行 → 回报 → 顺延”闭成环，并且每一步都留下证据。**

## 2. 核心闭环

```
        ┌──────────── 08:30 发今日工作项 ────────────┐
        │                                            ▼
   00:00 收尾                                    人／agent 执行
   顺延＋重排明日                                  （勾选完成 / 评论原因）
        ▲                                            │
        └── 21:00–23:30 每30分钟催促 ◄── 20:30 询问进度 ◄┘
```

| 时间 | 动作 | 做什么 |
|---|---|---|
| 08:30 | morning | 读 `plans/今日.json`，为每项工作建 Lark 任务（含子任务、起止时间），发“今日工作项”卡片 |
| 20:30 | evening | 读任务勾选与评论，算完成度，发“今日进度询问”卡片 |
| 21:00–23:30（每 30 分） | chase | 没完成又没说明原因的，发“请点击完成”卡片催促；全部完成或已说明就停 |
| 00:00 | close | 判定是否旷工；未完成项**沿用原任务改期**顺延；定稿次日计划文件；需求仍不足再要一次 |
| 白天（每小时，launchd）／11、14、17 点（过渡定时任务） | sync | 把进度写回本地（进度快照、任务卡 `status`／`progress`），维护次日计划草案，需求不足就在 Lark 要，刷新本地看板 |

**每个命令结束时都会做同一组收尾动作**：同步进度、回写任务卡、读取用户补充的需求、维护次日计划、刷新看板。所以你随时打开看板，看到的都是最近一次运行时的真实进度，不依赖你记得手动生成。

## 3. 设计原则

1. **证据优先，不替人宣称完成。** “完成”只有一种来源：你在 Lark 任务里勾选。监工看不到你的工作成果，所以它**永远不会**把“没证据”当成“已完成”，也不会替你报完成。
2. **回应方式用平台原生动作，不发明格式。** 勾选任务、在任务评论写原因、对提问消息点“回复”——都是 Lark 自带的操作。不要求你背格式、不要求你开新工具。
3. **顺延，不重建。** 没做完的任务不是新建一个副本，而是把原任务改期。评论、历史、子任务进度都留在原处，任务列表也不会被重复项污染。
4. **有原因就是有回应。** 做不完可以，但要说为什么。有评论说明＝有回应，不算旷工。
5. **旷工的定义很窄，并且标明可信度。** 旷工＝全天没有任何主任务被勾选、没有任何评论、对提问也没有回复。它只代表“没回应”，不代表“没做事”；若当天追问次数不足（例如电脑休眠），记录里会注明可信度较低。
6. **定时动作是确定性的，不依赖 LLM。** 定时任务只跑脚本（`scripts/supervisor.py`）。AI 的价值在“写计划、拆任务、分析原因”，不在“准点发消息”。这样断网、换模型、换 agent 都不影响监工准时。
7. **文件就是总线。** 计划、任务、日志、状态都是仓库里的文件。任何 agent 只要会读写文件就能参与，不需要绑定某个工具或对话。
8. **只用 REST，不碰别人的连线。** 与其他系统（例如已占用机器人长连接的另一个 agent）共用同一个 Lark 机器人时，监工只调用无状态的 REST，不开第二条长连接，避免抢消息。
9. **失败要出声。** 脚本失败会写 `*-supervisor-error.md` 并尽力在群里发“监工执行失败”，不能静默。
10. **可关闭、可回滚。** 一条命令卸载定时任务；所有私有数据都在不入库的目录里。
11. **本地要跟得上 Lark。** Lark 是“事实发生的地方”，本地是“别的 agent 读取的地方”。每次运行都把 Lark 的进度写回本地（进度快照、任务卡），否则本地文件与看板会悄悄过期，agent 就在旧信息上做决定。
12. **次日计划不是 00:00 才冒出来。** 它从白天开始就以“草案”形式持续维护，晚上询问进度时已经存在；到 00:00 才定稿。这样才能在你还醒着的时候发现“明天没事可做”。
13. **没需求就主动要，而不是默默空转。** 计划工时低于下限，监工会在 Lark 说“需求不足”并告诉你怎么补；你回复的每一行都会变成计划项。有次数与间隔限制，避免变成骚扰。
14. **估时是需求充足与否的基础，不能缺。** 任务卡没写 `est_hours` 会被当成 1h，大任务被低估就会误报“需求不足”。这是实际发生过的错误（见 docs/what-was-done.md）。

## 4. 角色

| 角色 | 职责 | 不做什么 |
|---|---|---|
| **人** | 做事；在 Lark 勾选、写评论；决定优先级 | — |
| **执行 agent** | 领任务卡、做事、写日志、勾验收项 | 不改别人认领的任务；不改 `.supervisor/` |
| **计划 agent（可选）** | 写 `plans/YYYY-MM-DD.json`：把任务卡拆成时段与子任务 | 不整个覆盖别人的计划 |
| **监工脚本** | 定时发任务、发卡片、收集结果、催促、顺延、记旷工 | 不判断工作质量；不替人完成 |

## 5. 名词定义

| 词 | 定义 |
|---|---|
| 工作项 | 计划文件 `items[]` 的一条，对应一个 Lark 主任务 |
| 主任务／子任务 | 工作项／工作项下的细分清单（Lark 子任务，默认不指派，避免刷屏任务列表） |
| 完成 | Lark 任务被勾选完成（`completed_at` 非 0） |
| 有说明 | 未完成但用户在任务评论写了原因 |
| 回应 | 完成、有说明、或对提问消息有回复，三者任一 |
| 旷工 | 当日没有任何回应（见原则 5） |
| 顺延 | 未完成主任务改期到次日，并排在次日计划最前 |

## 6. 已知限制

- 定时任务要求电脑当时开着；休眠期间的触发会在唤醒后补跑，但可能晚于预期，追问次数也可能不足。
- 监工只能依 Lark 与仓库证据判断，看不到你的设计稿／代码本身。
- Lark 没有给应用发起原生“投票”的接口；卡片按钮若要回传结果必须走回调（长连接或 webhook），本系统刻意不用，因此卡片只有展示与开链接。
- 评论读取依赖机器人应用的任务／消息读取权限，见 docs/setup-macos.md。

## 7. 非目标

- 不是项目管理工具，不管甘特图、资源、预算。
- 不评价工作质量，不给绩效分数。
- 不替代 issue tracker：它只负责“今天的事有没有被做、没做的怎么办”。
